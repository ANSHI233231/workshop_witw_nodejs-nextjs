# Agent rules for this repo

Rules for anyone working in this repo, human or AI agent. This file is intentionally short and grows as the project takes shape; how each part works is in `docs/how-it-works/`.

## Project structure

- **Separate apps under `apps/`.** Each app has its own `package.json`, `node_modules`, `.env` and build. There is no root workspace, so run every command from inside the app it belongs to.
  - `api`: Node.js API used by all the frontend apps
  - `manage` (port 3041 locally): Next.js app for superadmin operations: users and roles, logs, background jobs, languages, the technical documentation
  - `web` (port 3040 locally): Next.js portal app: the public website (welcome page, sign-in, forgot password) and the signed-in portal
- **`init.js` at the root sets up a copy of the repo** (a developer's machine, staging or production): the `.env` files with new secrets, the database and its migrations, the packages, the first Super Admin, git. `node init.js --help` lists its options; `--dry-run` shows what it would do. It runs once per machine: on a machine that is already set up (`apps/api/.env` exists) it does nothing unless `--force`. It uses Node's own modules only (there is no root `package.json`). A new setting an app needs at setup goes into its `.env.example` and, when it differs per environment, into `init.js` in the same change.
- **Process manager files live in `environments/`**: one pm2 file per copy (local, staging, production) and their port table. `ecosystem.local.config.example.js` is committed; each developer copies it to `ecosystem.local.config.js` (git-ignored) with ports free on their machine. A new app is added to the example and both server files together. See [environments/README.md](environments/README.md).
- **Docs live in `docs/`.** See [docs/README.md](docs/README.md). `docs/prototype/` is a **git submodule** (the separate prototype repo), set up by `init.js` as a copy of the starter prototype ([prototype](docs/how-it-works/platform/prototype.md)): treat it as read-only reference here; every new feature goes through the prototype before it is built; in the starter repository itself, a change to a starter screen updates its board in the starter prototype in the same piece of work; changes go to the prototype repo, and moving its pin (`git submodule update --remote docs/prototype`) is a deliberate commit.
- **Word documents are generated, never edited.** A `.docx` listed in `docs/tools/docx-generator/docs.config.json` (the `.md` in `docs/how-it-works/workflows/`, the `.docx` in its `documents/` folder) is generated from its `.md`. Edit the `.md`, run `npm run diagrams` if a Mermaid diagram changed, then `npm run build` in `docs/tools/docx-generator` (after `npm ci`), and commit the `.md`, the `.docx` and the diagram images together. `npm run check` must pass: it fails when a `.docx` is out of date with its Markdown. Never hand-edit the `.docx`, and never upgrade the generator's libraries or change its styling in the same change as a document edit, because that changes every document's output. See [its README](docs/tools/docx-generator/README.md). **The technical document is changed only when the user asks for it**, never as part of another task; if something in it becomes out of date, say so instead.
- **Use only the parts of the prototype the user has declared ready.** **Which boards are ready is recorded only in [docs/PROTOTYPE-SYNC.md](docs/PROTOTYPE-SYNC.md)** (its Ready column: the prototype commit and the date the user declared it), not here. **A screen is copied whole:** every part of it is shown, even what has no behaviour yet, and its parts are then made to work one by one; never leave a part out because it doesn't work yet. **Every board's state is tracked in [docs/PROTOTYPE-SYNC.md](docs/PROTOTYPE-SYNC.md)**: built or not, our route, and each difference with its reason, plus our screens with no board; update its row in the same change as the screen, and re-check it when the prototype pin moves. **Not ready:** every other screen: don't build from those until the user says so. Never change the prototype from this repo.

## API

The API is a **modular monolith**: one codebase, one process, split into business modules with enforced boundaries. Full layout in [apps/api/README.md](apps/api/README.md); module anatomy in [apps/api/src/modules/README.md](apps/api/src/modules/README.md).

- **Modules.** Each business area is one folder in `apps/api/src/modules/<module>/`, holding its own routes, controllers, services, repositories, sql, validators, dto, mappers, contracts and types. A module creates **only the folders it needs**.
- **`index.ts` is a module's only public surface** and its composition root (`createXModule(deps)`). Code outside a module imports only its `index.ts`, never its folders.
- **Layering inside a module:** `routes → controllers → services → repositories → sql`. Controllers are thin and depend on the service contract; business rules live in services; **repositories are the only layer that runs SQL**, and the SQL itself lives in `sql/<entity>.sql.ts` as named statements.
- **Writes are owned, reads are open.** A module INSERTs / UPDATEs / DELETEs only its own tables; a change to another module's data goes through that module's service. SELECTs may JOIN any table (other modules' tables, global masters) for lists, detail pages and reports. A read with business meaning ("is this user active and allowed to sign in?") still goes through the owning module's service, so the rule lives in one place.
- **Cross-module calls go service → service contract**, handed in through `createXModule(deps)` in `src/routes/index.ts`. Never import another module's repository, and never write to its tables.
- **Shared code:** `core/` (context, exceptions, errors, http, logger, validation) never imports modules. `database/` holds the connection and transactions. `infrastructure/` holds adapters to outside services (email, SMS, payment, storage, queue, cache): one folder per capability with a provider-neutral contract, a factory, and `providers/` per vendor. Modules depend on the contract only, never on a provider or vendor SDK; adapters are built in `server.ts` from config and injected. See [apps/api/src/infrastructure/README.md](apps/api/src/infrastructure/README.md).
- **Configuration** is read only in `src/config/` (zod-validated) and imported only by entry points (`server.ts`, the CLI). `app.ts` and modules receive what they need. Never give a secret a fallback value; a new variable goes into `environment.schema.ts` and `.env.example` together.
- **Errors:** throw an exception from `core/exceptions` with a `SCREAMING_SNAKE` code (`USER_NOT_FOUND`). Controllers have no try/catch; every async handler is wrapped in `asyncHandler()` in its route file and responds with `ok()` / `created()` / `noContent()` / `paginated()` / `sendDownload()` from `core/http`. Nothing outside `core/` writes to `res` itself (`res.json`, `res.send`, `res.status` …): `npm run lint` fails on it, and a response the helpers don't cover gets a new helper in `core/http`.
- **Validation** is a zod schema in the module's `validators/`, applied with `validate(schema)` in the route.
- **SQL transactions are ambient:** a service that needs several writes (its own and other modules') to succeed or fail together wraps them in `this.db.transaction(async () => …)`; every query inside, in any module, joins automatically. No `tx` parameter on any method. Only the service that starts the operation opens it; no emails, gateway calls or uploads inside it. See [docs/how-it-works/platform/sql-transactions.md](docs/how-it-works/platform/sql-transactions.md).
- **Every write records an audit event.** A service that creates, updates or deletes calls `auditService.record(...)` inside the same operation (with what changed), and `auditService.recordFailure(...)` in its `catch` after the transaction; the module gets `auditService` through `createXModule(deps)`. Action codes are numbers in `modules/audit/types/audit.types.ts`, a module's in its hundred. See [modules/audit](docs/how-it-works/modules/audit/README.md).
- **Logging** goes through `core/logger`, never `console.*`. In a module use `logger.category('<module>')`; pass context as an object and errors as `{ error }`; when re-throwing keep the original as `cause`. Every line gets `[ip][userId][requestId][level][category]` and a trace of our code automatically; SQL lines and request dumps are `info`. `.env` has just `LOG_ENABLED` and `LOG_LEVELS`; keep the advanced overrides out of `.env` unless there's a reason. Files per level in `apps/api/logs/`. Never log secrets. See [docs/how-it-works/platform/logging.md](docs/how-it-works/platform/logging.md).
- **URLs:** every module mounts under `/api/<module>` in `src/routes/index.ts`, the single mount point. There is no version prefix (no `/v1`): the only clients are this repo's apps, released together with the API. **Routes are by module, not by frontend app** (`/api/users`, `/api/language/master`): no per-app prefix; who may call a route is decided by the route's own access.
- **Every route states its access.** Routes are added only through `apiRouter()` from `core/http`, whose second argument is the access (`publicAccess`, `auth.access.session`, `.signedIn`, `.roles([...])`, or a module's `key`): a route without it doesn't compile, and lint forbids express's `Router` and `app.get(...)`. A new `publicAccess` is a deliberate choice, named in the planning file; `npm run cli route/list` shows every route and its access. See [docs/how-it-works/platform/route-access.md](docs/how-it-works/platform/route-access.md).
- **CLI.** `apps/api/src/cli/` is the controller/action console framework: `lib/Application.ts` auto-discovers `controllers/*Controller.ts`, and each `actionXxx` method becomes `npm run cli <controller>/<xxx> [args]` (`cli:dist` for the compiled build / cron). New maintenance or one-off tasks go here, not in ad-hoc scripts. A controller with its own helper files gets a sub-folder (`controllers/<tool>/`); every `*Controller.ts` under `controllers/` is discovered. A command builds a module from its `index.ts` with `this.db` and calls its service, never its own SQL. A destructive command defaults to a dry-run and needs an explicit `confirm` argument to write.
- **Background jobs** are CLI commands run by the worker the API starts (`WORKER_ENABLED`): scheduled, planned or queued by a module (`IJobQueue.enqueue`), managed in Console › Platform › Background Jobs. A new background task is a new CLI command (exit code 0 = done, a short summary on stdout, dry run unless `confirm`, safe to run again); never a separate script or system cron. See [docs/how-it-works/platform/background-jobs.md](docs/how-it-works/platform/background-jobs.md).
- **Old-database access (copying an old system's data, if the project has one) exists only in the CLI**, always as a read-only MySQL session; the API server never connects to it. **A released copy command is never changed; a change is a new command**: once committed, someone may already have run it. A plain bug fix that keeps what it copies (a crash, a wrong message) is not a change of what it copies.
- **These boundaries are enforced by `npm run lint`** (eslint-plugin-boundaries). Don't disable a boundary rule to make an import work; if a dependency seems necessary, raise it with the user.

## Frontend apps

`manage` and `web` are separate Next.js 16 apps (App Router, React 19, TypeScript, Tailwind CSS v4) with the same structure. Full guide: [docs/how-it-works/platform/frontend-apps.md](docs/how-it-works/platform/frontend-apps.md).

- **No shared code.** The apps don't import each other or the API; there is no shared package. A component needed in two apps is copied, and the copies are kept identical.
- **Type folders** under `src/`: `app/` (routes only), `components/ui|layout|<feature>/`, `hooks/<feature>/`, `services/`, `types/`, `lib/`.
- **Only `src/services/` calls the API**, through `services/api-client.ts` (the only `fetch`). Pages, components and hooks call `services/<feature>.service.ts`. Screens branch on `ApiError.code`, never on message text.
- **`process.env` is read only in `src/lib/config.ts`** (public `NEXT_PUBLIC_*` values, which reach the browser: no secrets) **and `src/lib/server-config.ts`** (server-only values), both zod-validated.
- **Design tokens** are defined in `src/app/globals.css` `@theme` and used by name (`bg-brand`, `text-muted-foreground`). No raw hex in components; Tailwind v4 silently drops a class whose token doesn't exist, so confirm a token is defined before blaming styling elsewhere.
- **Read `node_modules/next/dist/docs/` before using a Next.js API.** Next.js 16 has breaking changes (e.g. `error.tsx` receives `retry`). Each app's `AGENTS.md`/`CLAUDE.md` is generated by `next dev` and stays committed.
- **Hiding a link is not access control.** Restricted pages are guarded at the route-group layout, and every restricted API call is enforced by the API.
- **Logging:** use `logger` from `@/lib/logger` (same import on server and client; `logger.category('<feature>')`). Browser `console.*`, crashes and server errors are captured automatically into the app's own `logs/` folder; browser logs go only to the app's own `/client-logs`, never the API. Settings `LOG_ENABLED` / `LOG_LEVELS` in each app's `.env`. See [docs/how-it-works/platform/frontend-logging.md](docs/how-it-works/platform/frontend-logging.md).
- The layer rules above are enforced by each app's `npm run lint`.

## Database & schema

- **No ORM.** Queries are hand-written SQL via `mysql2`, with `?` placeholders for every value. The only things ever interpolated into a SQL string are identifiers (table/column names) the code chooses from a closed set, never anything taken from a request.
- **Never auto-apply schema changes.** Write a dated migration file in `apps/api/src/database/migrations/` named `YYYY-MM-DD-<short-slug>.sql`: a short header comment explaining the change and linking the planning file, then the DDL. The user runs it themselves. There is no migration runner, and executing DDL against a shared database is not the agent's call.
- **Never edit a migration once it has been applied.** The schema starts from the base set (six files dated 2026-10-28 in `apps/api/src/database/migrations/`, one per module that writes the tables, listed in its README, which build a blank database). Every later change lives only as a new dated file there, and the current schema is the base set plus the later files, read in date order. A new dated file stays editable until it is committed and live: while its feature is being built, the feature's further schema changes and its starting rows (inserted at the end of the file) go into that same file. Every data change after that is a CLI command.
- **Wire a new field through every layer in the same change:** the migration, the repository (INSERT column list and UPDATE mapping), the zod validators and DTOs (create and update), the mapper's row → response mapping, and the frontend types and forms of every app that uses it. A response mapping that leaves out the new field is a silent bug: the edit form loads the default, and the next save writes that default over the real value. After wiring it, `GET` it through the live API and confirm the key is there.
- **Verify data bugs against the live system.** When a bug is data-shaped (stale value, missing field, wrong persistence), `curl` the endpoint or query MySQL directly before saying it's fixed, rather than reasoning from code alone.

### Database conventions

1. `snake_case` for every column name in the DB; `camelCase` in TypeScript.
2. No foreign-key constraints in the DB. Every column that points at another table gets an index instead.
3. **Table names are singular, and a column that points at another table is that table's exact name plus `_id`**, in every table: `master_district` → `master_district_id`, `user` → `user_id`. So `master_block.master_district_id`, never `district_id`; strip `_id` and you have the table. If the singular is a MySQL reserved word (`order`, `group`, `key`, `condition`), choose a clearer name (`customer_order`). Exception: the audit columns `created_by`, `updated_by`, `deleted_by` (they point at `user` but are named for what they record).
4. All timestamps are `DATETIME`, stored in UTC.
5. Soft delete: a deleted row gets `status = -1` and is never physically removed. `status = -1` is what marks it deleted; `deleted_at` / `deleted_by` record when and by whom where a table needs them.
6. Column names describe purpose, not type. Avoid generic names like `data`, `value`, `info`, `flag`; use names that explain what the column means in the business domain.
7. **Fixed values are stored as numbers, never as text.** Any column whose values come from a fixed set the application defines (status, type, kind, mode, role, state, any category) is a `TINYINT` (or `SMALLINT` if it can grow past 127), never a string like `'active'` / `'inactive'`.
   - The number → meaning map is defined once in TypeScript as an `as const` object (in the module's `types/`, or `core/` when shared), never the `enum` keyword: `export const UserStatus = { ACTIVE: 1, INACTIVE: 2 } as const;`. Code always uses the named constant (`UserStatus.ACTIVE`), never a bare number or string.
   - The map is also written in the header comment of the migration that creates the column.
   - Codes start at 1 and are append-only: never renumber, never reuse a retired code. `-1` stays reserved for soft-deleted rows (convention 5); `0` is not used as a meaning.
   - No `ENUM` column type and no `CHECK` constraint listing the values: the API validates them (zod schema + the constant).
   - Yes/no columns stay boolean (`TINYINT(1)`, named `is_…` / `has_…`): a two-value flag is not a code set.
   - Exception: values defined by someone else keep their standard form: currency (`'INR'`), country and language codes, time zones, MIME types, payment-provider names. If unsure whether a set is ours or external, ask.
8. **Global master tables start with `master_`.** Reference data used across modules and apps (locations, categories, types managed by the superadmin) lives in `master_<name>` tables (singular): `master_country`, `master_language`. Indexes follow the table: `idx_<table>_<columns>`, e.g. `idx_master_block_master_district_name`. Tables owned by one feature use that feature's own name, without the prefix. A master that belongs to one area (each tenant's own list, managed by that tenant) is `<area>_master_<name>`.
9. **System tables start with `meta_`.** Values the system itself runs on, which code refers to by fixed ids (roles: `meta_role`), live in `meta_<name>` tables. Their rows are written by migrations, only when needed; they have no create / edit / delete screens. `master_` tables, by contrast, are operational data the superadmin changes any time, with screens.
10. **Text widths:** names `VARCHAR(150)`, descriptions `VARCHAR(1000)` in the database; the stricter limits a screen needs are enforced in the API and the forms.
11. **Small fixed sets live in code** (rates, natures, statuses); a table only for lists that grow or are managed on a screen. Their values are data, never hard-coded in screens.

## Working rules

- **Plan before code.** Planning files are the single source of requirements (there is no separate SRS). Every new feature or significant change gets a planning file at `docs/planning/features/<YYYY-MM-DD>-<short-slug>.md` before any code is written. Copy [docs/planning/TEMPLATE.md](docs/planning/TEMPLATE.md) to start one.
- **Every test case is run in the browser and its result written.** Each §3 test case is run by the agent with Playwright on the real screens (or `curl` / the CLI / a query when it has no screen) and gets its PASS / FAIL line in §5 before the plan is `shipped` ([browser testing](docs/how-it-works/platform/browser-testing.md)).
- **`docs/how-it-works/` is the source of truth for how things work today.** One short, plain-language doc per module flow, workflow, role or process, filed by section: `platform/`, `modules/<module>/` (same name as the code module), `workflows/`, `roles/` (see [docs/how-it-works/README.md](docs/how-it-works/README.md)). It describes the present only; history stays in planning files. Read the relevant doc before changing an area.
- **Keep the planning status true.** Set `in-progress` when work starts, and `shipped` with the `Shipped` date in the same change that completes the work, before committing. A finished feature's planning file never stays `in-progress`. Later fixes to a shipped feature are logged in its §4/§5/§6; the status stays `shipped`.
- **Check existing plans first.** Before starting work or fixing a bug, look through `docs/planning/features/` for an existing file covering that area.
- **Record every user decision in the planning file, as it happens.** If the user answers a question, changes a requirement or adds a constraint, write it into the planning file in the same turn. When a later instruction replaces an earlier one, mark the earlier one superseded instead of deleting it. Asking about an option is not deciding it: record only a clear decision.
- **Ask on architecture decisions.** When a change needs a product or architecture decision, ask before implementing. Don't pick the more invasive option on your own, and build only what was asked: suggest extras instead of adding them.
- **Verify before calling it done.** Run `npx tsc --noEmit` in every app you touched (plus `npm run lint` in `apps/api`), and `npm run build` before calling frontend work done; then run the feature's test cases ([browser testing](docs/how-it-works/platform/browser-testing.md)). A passing build is not a passing test.
- **No comments in code.** Don't write comments, including at the top of files: when the code changes, a comment stays behind and the file ends up saying two different things. Make the code explain itself (clear names, small functions); explanations belong in `docs/how-it-works/` and the planning files. Only comments that tools require are allowed: lint directives (`eslint-disable…`), bundler hints (`/*turbopackIgnore: true*/`), and the CLI's `/** … */` above each `actionXxx` (it becomes the `--help` text). Code copied unchanged from elsewhere keeps its comments unless asked.
- **A UI pattern change is applied everywhere at once.** A field that becomes a searchable dropdown, or a new rule for a kind of field, changes in every equivalent place in every app in the same change.
- **Run prettier only on the files you changed**, never on folders or on CSS copied from the prototype.
- **Clean up after diagnostic work.** Delete scratch files and uninstall temporary dependencies once you're done.

## Sync discipline

- **Frontend validation must mirror backend validation.** Any rule enforced on one side (required, min/max, format, uniqueness) must have an equivalent on the other. Update the frontend form schema and the API DTO/service check in the same change.
- **DB schema changes require a migration.** No schema change ships without a dated `.sql` file in `apps/api/src/database/migrations/`, run by the user. This applies even to changes that look trivial, like a nullable column or a new index.
- **API boundary changes ship together.** When changing anything that crosses the API boundary (DTOs, response shapes, route paths), update every frontend app that uses it in the same change.
- **Deleting a Next.js app's `.next` folder requires restarting its dev server.** Otherwise every route of that app 500s with ENOENT. `npm run build` stays green meanwhile, so a passing build is not proof the app works. After deleting `.next`, restart the app and `curl` two or three routes before calling the change verified.
- **Use the dev hostname, not `localhost:<port>`, once one is configured.** If an app's API URL points at a hostname, loading the app by its raw port makes every API call cross-origin, and the page fails with a generic "Network Error". Also, `curl`ing a route only proves it renders server-side; it exercises no client-side API call. Each app's `DEV_ALLOWED_ORIGINS` must list its hostname. Full setup: [docs/how-it-works/platform/local-development.md](docs/how-it-works/platform/local-development.md).
- **Backend config changes need a process restart.** The dev server picks up source changes but not `.env` changes or process-manager (pm2) settings. After changing either, restart the API and confirm the new value took effect.
- **Behaviour changes update `docs/how-it-works/` in the same change.** A new or changed module, feature, workflow or role isn't done until its doc there is current. If the code and the doc disagree, that's a bug: fix whichever is wrong.
- **New features get new test cases, and every one is run.** Design test cases in the planning file's §3 before implementation. Run each one yourself: **in the browser with Playwright** for anything a user does on a screen (desktop and phone width, console errors, failed calls), with `curl`, the CLI or a query only for cases with no screen. Record each one's PASS / FAIL / NOT RUN, method and what was seen in §5 as soon as it is run; a feature is not `shipped` while a case is FAIL or has no line. The planning file is the only place test cases and results live; there is no separate test plan. How: [docs/how-it-works/platform/browser-testing.md](docs/how-it-works/platform/browser-testing.md).
- **Test data must be cleaned up.** Any test data written to the database or a shared environment while verifying something (a test row, a changed field, an uploaded file) is removed or reverted once verification is done. Test users and rows carry a marker (`ct_*` usernames) and are deleted by that marker, never by id ranges.
- **Commit only when the user asks**, for that batch; earlier approval does not carry over. Commit messages end at the body: never add `Co-Authored-By: Claude ...`, "Generated with Claude Code", or similar, in commits or PR descriptions.
- **Sensitive files never enter git.** `.env` files, credentials, private keys, real secrets and server addresses are never committed. Check `git status`/`git diff` before staging, stage files explicitly (never `git add -A` or `git add .`), and never weaken `.gitignore` to let these through.
