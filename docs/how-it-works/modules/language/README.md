# Language (languages and translations)

**What it is.** The languages the apps offer and the translation of their screen texts from English into the other languages. The Super Admin keeps the translations in the console; **Publish translations** writes them to a JSON file that each app reads while running, so the apps never read translations from the database on a page load. The manage console and the web app use it. English is the only language seeded; others are added in the console.

**Who uses it.** The Super Admin (manage › Languages). Every console and portal user sees the language switch in the header (one button per published language, its short name).

## The flow

1. **Languages** (manage › Languages › Language Master, `/languages/master`): the list of languages (name, native name, short name, code, Shown in, Default for, status), add, edit, switch on / off; no delete. The **code** (`hi`) is the language's key: set when the language is added, locked on Edit. The **short name** (EN, हि) is what the header switch shows. **Where it is shown** is a grid of the places (Manage, Web Portal, Web Website) with a **Shown** and a **Default** tick each:
   - **Shown**: the language is offered on that place's switch. Hiding it there keeps the record (soft delete) and ticking it again brings it back.
   - **Default**: the language that place starts in before a visitor picks one. Each place has exactly one default, which must be shown there; ticking it on one language takes it off the other, and a default can't be unticked or hidden without giving the place another one.
   - **English** is the base language: shown everywhere (its Shown ticks are locked) and can't be switched off (`LANGUAGE_BASE_LOCKED`); its status switch shows on and locked, with the tooltip "English is the base language". Any other language can be switched off, even a default: the places it was the default for go back to English in the same save, and its Shown places are kept for when it is switched on again.
   - No website has a language switch or translated text yet; its list and default are published ready for them. English starts shown everywhere and the default everywhere.
   - **A save takes effect at once:** every add, edit or switch on / off rewrites each app's `languages.json` (audit 1623, 1624 on failure); no Publish is needed. A language is listed in an app only once its texts have been published there (its `<code>.json` is in the app's folder); English is always listed.
2. **App Translations** (screen text; manage › Languages › App Translations, `/languages/translations`): one row per English text with one column per other language beside it (`hi_text`, `ta_text`, …; empty = the English shows). The page shows a column and an edit field for each active language that has a column; English and the language columns share the width equally, Status and Updated On stay narrow. Search covers every language; the "Missing" filter picks one language. Add, edit, switch on / off.
3. **Download** gives `language-translations-<date>.csv` with the columns "English Text" and "<Language> Text" for each language ("Hindi Text", …), every active row, **every cell in quotes**, so a spreadsheet never splits a text at a `;` or `,` inside it (some old texts hold `&#x00A0;`) whatever separators its import uses.
4. **Upload** takes such a CSV (at most 2 MB, 5,000 rows). With a header row, its columns are matched by name ("Hindi Text", or the code); a column naming no language with a column is refused. Without a header, the columns are English then the languages in the page's order:
   - a row whose English already exists updates that row's Hindi, never adds a second row; a row is added only when no row matches. "Matches" is the database's own rule for the unique English text: ignoring case, the spaces around it and accents (`Save` = `save`, `Café` = `Cafe`);
   - an empty cell leaves that language's existing text as it is;
   - the header and blank rows are skipped; a row with no English, a text over 500 characters or an English already earlier in the file is refused with its row number;
   - the valid rows are written together, in one transaction, and the result shows added / updated / unchanged / refused.
5. **Publish translations** writes the screen texts into each app folder listed in the API's `TRANSLATION_DIRS` (`app=folder`, like `LOG_VIEWER_DIRS`), then rewrites `languages.json` as a Language Master save does:
   - `<code>.json` per active language with a column: `{ "<english text, trimmed, lower case>": "<text>" }` from the active rows that have that language (a switched-off language's file is removed);
   - `languages.json`: the languages shown on that app's portal (`languages: [{ code, name, nativeName, shortName }]`) and its default (`defaultLocale`); for web also those of its public website (`websiteLanguages`, `websiteDefaultLocale`). Only active languages with a translation column are listed. An app gets a `<code>.json` only for a language its portal or website shows; the others are removed from its folder.
   The page shows **Last published**: the newest date of the `<code>.json` files (who published is in the audit log). A changed text reaches the apps only when Publish is pressed; a Language Master change reaches them on save.
6. **In the app** (manage and web; `src/lib/i18n/`, the same files in each): the languages come from `languages.json` (only English when there is no file yet), so no language list is written in the app's code; the header's switch shows one button per language, with its short name. The language shown is the `locale` cookie when it names one of those languages, else the app's default from `languages.json`, else the first language listed; the cookie is set by the switch (a year; domain from `NEXT_PUBLIC_LOCALE_COOKIE_DOMAIN`, empty = this host). The server reads `translations/<code>.json` from the app's own folder, keeps it in memory and reads it again when the file changes, so a publish shows on the next page load with no rebuild or restart. `t('Save')` (server components, `serverTranslator()`) and `useT()` (client components; `TranslationProvider` wraps each app's root layout) return the chosen language's text, or the English given when there is none. A text with a value inside has a named slot: `t('Language "{name}" updated.', { name })`; the Hindi in the table keeps `{name}` where Hindi word order puts it, and the value is filled in after the lookup.

## Rules

- **Super Admin only:** both pages (console area `platform`) and every `/api/language` route except `GET /api/language/active`, which lists the active languages other than English (code, name, native name, short name) for anyone, signed in or not: the language switch and the translation fields of the forms need it on public pages too.
- **English is the key:** a page asks for the text in English, `t('Language Master')`; the lookup ignores case and the spaces around it. The texts are kept exactly as typed. A text new to the table shows in English until its Hindi is added (App Translations page) and published.
- **What is translated in manage:** every text the app owns (frame, pages, dialogs, toasts, form messages, the shared pager / Export / switches / status cards, tab titles, sign-in and forgot password) and the API's messages shown on screen. **Not:** data from the database, dates and numbers, log lines, the audit log's names from the API, and exported CSV files (they stay English).
- Checks, the same in the API and the forms (a taken name, code or English text shows "This name / code / text is already in use." under its field): language name 2–100 characters, unique; native name up to 100; short name required, up to 10; code two small letters (`hi`), unique; Shown in required (the places); a default must be shown there (`LANGUAGE_SITE_RULE`); Default for: the places; English required, up to 500, unique ignoring case; Hindi up to 500.
- **A new portal or website** needs no migration: a new code in `LanguageSiteCode` and its name in the API's and manage's site lists (`LANGUAGE_SITES`), and its app's folder in `TRANSLATION_DIRS`.
- **Needs the same server** as the apps (the API writes into their folders), as the logs do. The files are not in git (`apps/<app>/translations/` is ignored); the database is the source.
- **A new language gets its column automatically:** after a language is added (and again after it is edited or switched on), the API adds `<code>_text VARCHAR(500) NOT NULL DEFAULT ''` to `app_translation` if it is missing (audit 417, 418 on failure). This is the one place the API changes the schema itself; it runs after the save's transaction, because MySQL commits any open transaction on `ALTER TABLE`, and the column name comes only from the validated two-letter code. The API's database user needs the `ALTER` right. A switched-off language keeps its column and texts. The API finds the columns from the table itself, so the page, CSV, Publish and the switch follow with no code change. Screen text keeps every language side by side in one row on purpose, so a whole row is easy to read, download and replace.
- Every write, upload and publish is in the audit log (module 4, actions 401–420; entities 3 language, 4 screen-text translation, 5 data translation).
- **Data text** (what users type into the database, such as a master's name) is translated separately, in `data_translation`, not in the JSON files (below).

## Data text

Free text stored in the database (a master's name, later descriptions) is translated row by row in **`data_translation`**: one row per table, record, column and language other than English (`entity_table`, `entity_id`, `entity_column`, `master_language_code`, `translated_text`). English stays in the table's own column.

- **A screen opts in, nothing is automatic.** The module declares which columns are translated and makes three calls to the shared `IDataTranslationService` (handed in by `createXModule(deps)`, like `auditService`): `apply(rows, [{ table, columns }])` on a list (one extra query; skipped when the language is English), `save(table, id, translations, columns, actorId)` inside its own create / update transaction (its changes go into the same audit entry), `forEdit(table, id, columns)` for the edit form. The request shape `translations: { <code>: { <column>: text } }` is `translationsSchema` in `core/validation`. An empty text clears a translation (status -1); an inactive language or a column not declared is refused on its field (`DATA_TRANSLATION_INVALID`).
- **The language of a request** comes from the `x-language` header (`core/context`, English when missing or unknown), for guests and signed-in users alike. manage's API client sends it from the `locale` cookie (in the browser) or the page's language (server pages).
- **The form** (manage `components/i18n/translation-fields.tsx`) shows one optional field per published language other than English (`languages.json`, the header switch's list), under the English field: label "Name (हिन्दी)", errors under the field. The edit form starts from the English text (`english`) and the saved translations.
- **Built today:** no screen uses data text yet; the service, `translationsSchema` and the form's `translation-fields.tsx` are ready for the first master that needs it. `GET /api/language/active` (open) lists the active languages other than English.

## Where it lives

- **Module:** `apps/api/src/modules/language/`
- **Endpoints:** `GET /api/language/active` (open); `GET|POST /api/language/master`, `PATCH /api/language/master/:code` (and `/status`), `GET /api/language/master/options`; `GET|POST /api/language/translations`, `PATCH /api/language/translations/:id` (and `/status`), `GET /api/language/translations/export`, `GET /api/language/translations/languages` (the languages with a column), `GET /api/language/translations/last-publish`, `POST /api/language/translations/upload`, `POST /api/language/translations/publish`
- **Tables:** `master_language`, `master_language_site` (where each language is shown and each place's default: `site` 1 Manage, 2 Web Portal, 3 Web Website, `is_default`, `status` 1 shown / -1 hidden), `app_translation` (screen text) and `data_translation` (data text), migration `2026-10-28-languages.sql`
- **Setting:** `TRANSLATION_DIRS` in `apps/api/.env`
- **Screens:** manage `/languages/master`, `/languages/translations` (`components/languages/`); in manage and web: `lib/i18n/`, `hooks/i18n/use-t.ts`, `hooks/i18n/use-languages.ts`, `components/i18n/translation-provider.tsx`
- **Data text:** `services/data-translation.service.ts`, `core/validation/translations.validator.ts`; manage `components/i18n/translation-fields.tsx`, `lib/i18n/translation-values.ts`.
